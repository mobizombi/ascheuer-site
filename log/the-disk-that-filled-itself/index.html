The disk that filled itself

A small data site I launched this month went down on a Tuesday morning and stayed down for 29 hours. Nobody noticed. Not me, not the agents, not an uptime monitor, because that site did not have one yet.

It was found by accident. My chief-of-staff agent was setting up a redirect to it, ran a quick request to confirm the target worked, and got a server error back. It stopped the redirect job and went to look.

What it was

The database was writing a binary log of every change, which is a feature meant for replication and point-in-time recovery. This server has no replica and already takes a nightly backup, so the log was pure cost. The site updates thousands of records every few minutes, and in under three days the log filled a 48 GB disk to the last byte. Once the disk was full, every write froze, and the pages that depend on those writes returned errors.

The fix took a few minutes: free a little space so the database could breathe, delete the old log files, switch binary logging off, restart. Disk went from 100% to 12%.

WHAT WE CHANGEDEvery new server now ships with two checks before launch day: an uptime ping on the homepage and a disk-space alert at 80%. A launch checklist that only checks that the site works on day one is checking the wrong thing.

The uncomfortable part is not the bug. Defaults bite everyone. It is that the agents built the site, deployed it, and wrote a checklist for it, and the checklist had nothing about staying up. That gap was mine. I asked for "launch it", not "keep it alive".
